magic_skill — Claude Code Subagent 原子化工作流

任务原子化拆解 → 干净上下文 Subagent → 结构化输出 → 审查机制

核心设计：一个规则问题进入系统后，Claude Code 作为调度器将其拆解为若干原子任务，每个任务由一个独立的 subagent 执行。subagent 之间不共享上下文，只通过结构化的数据包通信。每步输出必须经过审查才能进入下一步。

一、工作流总览

输入层
Input 用户问题
"AP操控闪电击，NAP操控幽灵选手。闪电击能造成伤害吗？"
Claude Code 读取 SKILL.md → 启动工作流
Step 1
Subagent query-decomposer
把自然语言问题拆成结构化查询计划
  • 提取牌名列表
  • 识别问题类型
  • 列出需要查的规则关键词
Output QueryPlan
{cards, rule_keywords, question_type, needs_rulings}
Check Schema 校验
输出是否符合 QueryPlan Schema？字段是否完整？
Schema 校验通过 → 进入并行查询
Step 2
并行
Subagent card-lookup × N
每个 subagent 只查一张牌
  • 输入：一个中文牌名
  • 调用 name_translator.py
  • 调用 card_search.py
  • 输出：CardInfo JSON
Subagent rule-lookup × N
每个 subagent 只查一个关键词
  • 输入：一个规则关键词
  • Grep + Read 本地 CR
  • 输出：RuleInfo JSON
审查
Check 牌面审查
每张牌都有 oracle_text？都有 scryfall_id？
Check 规则审查
每条规则都有 rule_number？来源都是 raw/cr/？
所有查询通过审查 → 合并证据包
Step 3
Subagent interaction-analyzer
基于证据包做深度解析，不查任何新信息
  • 输入：Evidence 包（所有查询结果）
  • 只基于传入的证据推理
  • 输出：Analysis JSON（含 needs_more_evidence）
Output Analysis
{conclusion, reasoning, confidence, cited_rules, cited_cards, needs_more_evidence}
Check 引用审查
结论中的每个引用都在 Evidence 中？
Check 迭代检查
needs_more_evidence 非空？→ 回到 Step 2 补充查询（最多3轮）
引用审查通过 + 无需补充 → 进入验证
需要补充证据 → 回到 Step 2 并行补充查询
Step 4
Subagent checker
独立验证证据和结论，不看推理过程
  • 输入：Evidence + Analysis
  • 硬检查：规则来源 + 牌面来源
  • 软检查：证据链完整性
  • 输出：Verdict JSON
Output Verdict
{status: PASS|WARN|BLOCK, checks, notes}
Verdict = PASS/WARN → 输出答案
输出层
Answer 最终答案
基于通过审查的证据输出最终答案
  • 引用具体规则条文
  • 标注置信度
  • verdict = WARN 时标注不确定点

二、审查机制设计

2.1 审查层级

层级触发时机审查内容失败处理
Schema 校验 每个 subagent 输出后 输出是否符合预定义 JSON Schema？字段是否完整？ 要求 subagent 重新输出
内容审查 查询类 subagent 输出后 牌面信息是否完整？规则来源是否为本地文件？ 标记缺失，进入下一步或 BLOCK
引用审查 analyzer 输出后 结论中的每个引用是否都能在 Evidence 中找到？ 要求 analyzer 补充引用或修正
迭代审查 analyzer 输出后 needs_more_evidence 是否非空？是否需要补充查询？ 非空则回到 Step 2 补充查询（最多 3 轮）
独立验证 checker subagent 不看推理过程，只看证据和结论是否匹配 verdict = BLOCK 时禁止输出结论

2.2 审查伪代码

# 每次 subagent 调用后的标准审查流程

function review_subagent_output(output, step_name):
  # 1. Schema 校验（强制）
  if not validate_schema(output, SCHEMAS[step_name]):
    missing = find_missing_fields(output, SCHEMAS[step_name])
    return {status: "RETRY", reason: "Schema 校验失败，缺少字段: " + missing}

  # 2. 内容审查（按步骤类型）
  if step_name == "card-lookup":
    if not output.oracle_text:
      return {status: "WARN", reason: "Oracle 文本为空"}
    if not output.scryfall_id:
      return {status: "WARN", reason: "缺少 scryfall_id"}

  if step_name == "rule-lookup":
    for match in output.matches:
      if not match.source_file.startswith("raw/"):
        return {status: "BLOCK", reason: "规则来源不是本地文件"}

  if step_name == "interaction-analyzer":
    for rule in output.cited_rules:
      if rule not in evidence.rule_numbers:
        return {status: "RETRY", reason: "引用了未查询的规则: " + rule}
    # 3.1 迭代检查：是否需要补充证据
    if output.needs_more_evidence:
      if iteration_count >= MAX_ITERATIONS:
        return {status: "WARN", reason: "达到最大迭代次数，证据仍不完整"}
      return {status: "ITERATE", missing: output.needs_more_evidence}

  # 4. 通过
  return {status: "PASS"}

# 4. checker 独立验证
function checker_review(evidence, analysis):
  card_ok = all(c.oracle_text for c in evidence.cards)
  rule_ok = all(m.source_file.startswith("raw/") for m in evidence.rules)
  evidence_complete = len(analysis.cited_rules) <= len(evidence.rules)
  return {status: "PASS" if (card_ok and rule_ok and evidence_complete) else "BLOCK"}

三、Subagent 设计规范

3.1 核心约束

每个 subagent 必须满足：
OK
上下文干净 — prompt 只包含该步骤的输入数据和执行规范，不含其他步骤信息
OK
单一职责 — 一个 subagent 只做一件事，不可再分
OK
输出稳定 — 相同输入必须产生结构相同的输出（Schema 约束）
OK
不共享状态 — subagent 之间不保留上下文，只通过数据包通信
OK
可审计 — 每个 subagent 的输入和输出都可以独立检查

3.2 Subagent 定义

query-decomposer

维度定义
职责把自然语言问题拆成结构化查询计划
输入用户原始问题（纯文本）
输出 Schema{cards: string[], rule_keywords: string[], question_type: string, needs_rulings: boolean}
工具无（纯文本分析）
上下文大小~200字（用户问题 + 拆分规则）
审查点Schema 字段完整性

card-lookup

维度定义
职责查询单张牌的 Oracle 文本和翻译
输入一个中文牌名
输出 Schema{input_name, english_name, scryfall_id, oracle_text, mana_cost, type_line, power_toughness}
工具Bash (name_translator.py, card_search.py)
上下文大小~100字 + 一个牌名
审查点oracle_text 非空、scryfall_id 存在

rule-lookup

维度定义
职责查询单个规则关键词的相关条文
输入一个规则关键词或编号
输出 Schema{keyword: string, matches: [{rule_number, rule_text, source_file}]}
工具Grep, Read
上下文大小~100字 + 一个关键词
审查点source_file 必须以 raw/ 开头

interaction-analyzer

维度定义
职责基于证据包做深度解析
输入Evidence 包（所有查询结果）
输出 Schema{conclusion, reasoning, confidence, cited_rules, cited_cards, needs_more_evidence?}
工具无（纯推理）
上下文大小~500字 + 证据包
审查点每个 cited_rules 必须在 Evidence 中存在

checker

维度定义
职责独立验证证据和结论
输入Evidence + Analysis
输出 Schema{status: "PASS"|"WARN"|"BLOCK", card_check, rule_check, evidence_check, notes}
工具无
上下文大小~200字 + 证据 + 结论
审查点不看推理过程，只看证据和结论的匹配度

四、数据包 Schema

# Step 1 输出: QueryPlan
{
  "cards": ["闪电击", "幽灵选手"], // 需要查询的中文牌名列表
  "rule_keywords": ["protection", "702.16"], // 需要查询的规则关键词/编号
  "question_type": "interaction", // interaction | rule | policy | format
  "needs_rulings": false, // 是否需要查 WotC 裁定
  "needs_strategy": false // 是否需要查策略文档
}

# Step 2 输出: Evidence (多个 card-lookup + rule-lookup 的结果合并)
{
  "cards": [
    {"input_name": "闪电击", "english_name": "Lightning Bolt", "oracle_text": "...", "scryfall_id": "..."},
    {"input_name": "幽灵选手", "english_name": "Burrenton Forge-Tender", "oracle_text": "...", "scryfall_id": "..."}
  ],
  "rules": [
    {"keyword": "protection", "matches": [{"rule_number": "702.16a", "rule_text": "...", "source_file": "raw/cr/7.md"}]}
  ],
  "rulings": [] // ruling-lookup 的结果（如有）
}

# Step 3 输出: Analysis
{
  "conclusion": "闪电击无法对幽灵选手造成伤害",
  "reasoning": "因为保护规则 702.16a 规定...",
  "confidence": "certain", // certain | likely | uncertain
  "cited_rules": ["702.16a", "702.16b"], // 引用的规则编号
  "cited_cards": ["Lightning Bolt", "Burrenton Forge-Tender"],
  "needs_more_evidence": null                     // 为 null 表示证据充足，否则列出需要补充的关键词
}

# Step 4 输出: Verdict
{
  "status": "PASS", // PASS | WARN | BLOCK
  "card_check": "PASS", // 牌面信息完整性
  "rule_check": "PASS", // 规则来源可靠性
  "evidence_check": "PASS", // 证据链完整性
  "notes": "所有检查通过"
}

五、与旧架构的对比

维度旧 magic-skill（Python pipeline）v3 旧架构（大 Agent）v3.1 原子化工作流
执行方式 Python 脚本串行执行 Claude Code 调用一个大 Agent 做所有事 Claude Code 调度多个原子 subagent
Agent 粒度 函数级 一个大 Agent（上下文 ~2000字） 原子级（每个上下文 ~100-500字）
上下文污染 无（代码分离） 严重（一个 prompt 包含所有步骤） 零污染（每个 subagent 只看当前输入）
并行能力 需自己实现 Agent 内部串行 Claude Code 天然并行调度
输出稳定性 高（代码确定性） 低（上下文太重，输出不可控） 高（上下文最小 + Schema 约束）
可审计 日志文件 只能看最终输出 每步中间产物可独立检查
失败定位 堆栈追踪 全量重试 步骤级定位 + 自动重试
审查机制 无 最终 checker 每步都有 Schema + 内容审查

八、实施路径
